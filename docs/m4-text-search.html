Names first, then text

Finding a file by name means comparing what you typed with a list already in memory: a few milliseconds. Finding a line inside files means opening and reading every one of them: hundreds of milliseconds for a big folder. Done on the same threads at the same time, the slow job would make every keystroke feel slow.

Think of a librarian with two jobs. Asked for a book, she first reads the titles off the catalogue cards and hands you that list at once. Only if you ask her to look inside the books too does she send an assistant to the shelves you pointed at, to leaf through them for your words. If you ask something new, she calls the assistant back straight away.

  • Asking for the books. Text search runs only after ⌘ T, shown by an “Inside Files” chip in the box. Without it, lines would crowd the names out of every search. ⌘ T again, or hiding the window, goes back to names.
  • The catalogue. Each keystroke runs the name search as in M3. Only once those names are on screen does the text search start.
  • The assistant. Text search runs on threads of its own, at macOS's lowest priority, so it uses the power-saving cores and gives way to anything more urgent. Lines arrive in small batches and are added under the names, up to 100.
  • Calling back. A new keystroke stops the text search at once, and any line found for the older search is thrown away rather than shown. Hiding the window stops it too, and drops its lines.
  • The shelves you pointed at. Only folders you add in Index Health are read; none are by default. Inside a folder you tabbed into, only the part of those folders inside it is read.

Cloud files are never downloaded

iCloud Drive and OneDrive can keep a file's name on your Mac while its contents stay online. Opening such a file to read it makes macOS download it. A text search that opened every file would quietly pull gigabytes down and fill your disk.

Think of a library whose shelves hold some empty book covers, each with a slip saying the book is in storage. The assistant reads the slip before opening the cover and moves on.

  • The slip. macOS marks a cloud-only file with a flag. Argus checks it before opening, and counts the file as cloud-only instead of reading it.
  • Belt and braces. The text search threads also tell macOS not to download anything for them, so a file that goes online in the middle of a search is skipped, not fetched.
  • Checked. Over iCloud Drive with 3,913 cloud-only files, tl grep skipped them, and 3,913 were still cloud-only afterwards (#31).

What remains

  • Big folders are slow to the first line: 0.7-1.5 s for all of ~/Documents. Listing all of home took 80-90 ms (#38), so listing the folder again for each search can't explain most of it; the time spent reading files before the first match is the likelier part, and it is not measured yet.
  • How fast a replaced search stops at background priority: 8-24 ms was measured at utility, one level up; the app runs at background.
  • Whole-home name search beside text search: 25.9 ms to 38.6 ms for 95% from Terminal on a busy Mac. Needs a re-measure on an idle Mac, and with nothing cached after a restart.
  • VoiceOver: the “Inside Files” title isn't announced as a group yet; the first try changed row heights and was taken out.
  • A licence notice: one library the engine uses, encoding_rs, carries a BSD-3-Clause part that needs a notice in shipped apps before a release carries text search.
  • Hand checks with the screen unlocked: the results window with lines in light and dark, and the + button's folder picker.
